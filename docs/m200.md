# Working on an M200 (G210)

## What is known, and what is not

The M200 is a CAN-bus mid-drive, so it sits on the bus as `DRIVE_UNIT` (0x02)
and speaks the same service protocol as the M400/M500/M600 family that both
upstream projects target.

Neither upstream project lists the M200 as tested hardware. Bafang reuses
block layouts across the family but has moved fields between firmware
generations (see the under-voltage disagreement in
[protocol.md](protocol.md#known-layout-disagreement)). So treat every field
name in `Parameter0/1/2` as a hypothesis until you have verified it on your
own motor.

## What the bus carries unasked

This firmware answers almost no realtime read -- `probe` reports
`ControllerRealtime0`, `ControllerRealtime1` and `SensorRealtime` as
unsupported -- and pushes the same data out as broadcasts instead. Everything
below was recorded from a `DP C340.CAN` display talking to a G210 on a 36 V
`BT360` pack. An excerpt is kept as `tests/data/display-interaction-excerpt.log`
so the codecs stay checked against bytes a real bike sent.

`monitor --passive` reads all of it without transmitting anything.

Rates are counted over the one capture that lost nothing, whose real duration
is recovered from the sensor's own counter (193 broadcasts x 11.46 ms = 2.21 s)
rather than from its timestamps, which are a buffer drain and 54x compressed.
Do not measure these from the 177-frame capture: it lost 53% of its frames, so
every interval in it reads about twice as long as it is.

### Decoded

| `041A6401` | `64/01` BatteryChargingInfo | 96 ms | `0B 00 62 17 5A 02` | 11 charge cycles, max 249d 10h uncharged, last 25d 2h |
| `02F83200` | `32/00` ControllerRealtime0 | 246 ms | `37 00 00 00 F1 04 04 10` | 55% charge, trip 0.0 km, cadence 0, torque 1265, range 41.0 km |
| `02F83201` | `32/01` ControllerRealtime1 | 246 ms | `00 00 00 00 1E 14 3F FF` | 0.0 km/h, 0.0 A, 51.50 V, controller 23 C, no motor sensor |
| `04F83401` | `34/01` BatteryState | 369 ms | `00 00 A3 0E 3D` | 0.0 A, 37.47 V, 21 C |
| `04F83400` | `34/00` BatteryCapacity | ~740 ms | `68 2B DF 17 37 31 64` | 6111 of 11112 mAh, RSOC 55%, SOH 100% |
| `02F83203` | `32/03` SpeedParameters | 2.00 s | `C4 09 C0 01 9D 08` | limit 25 km/h, 28" wheel, 2205 mm. Recorded here as "seen once" from a capture too short and too lossy to measure it; twelve later captures put it at 2.004 s, steady to +-0.01 |
| `02FF1200` | `12/00` ControllerState, op 7 | ~1 s | `07` / `00` | the live fault code: 7 = over voltage protection, 0 = no fault |
| `03106300` | `63/00` DisplayRealtime | 101 ms | `55 03 00 01` | 5 assist levels, currently 5, lamp off -- see below |
| `02F83207` | `32/07` OutputShaftCounter | 96 ms | `00 00 00 00 00 5A 06` | bytes 5--6, a u16 accumulator at 64 counts per turn of the output shaft |
| `02F83000` | `30/00` SystemUptime | 10.03 s | `35 00 00 00` | 53 ticks, so this drive unit has been powered for 8m 51s |

Periods from four or fewer frames (`34/00`) are order-of-magnitude only; the
capture is not long enough to pin them down.

Byte 3 of `31/00` is a rolling message counter. Neither upstream project reads
it, and it is the only thing on the bus that makes a dropped frame provable
rather than a guess -- `bafang_can.quality` uses it for exactly that.

`64/01` is not a broadcast: it is the battery answering a poll the display
sends about ten times a second. The answer is on the wire either way,
which is what makes it readable in listen-only mode where asking is not an
option.

### Three cross-checks that hold

Independent nodes deriving the same number from different fields is the
strongest evidence available that a layout is right, short of a reference tool:

* the battery reports 6111 of 11112 mAh in `34/00`, and 55% RSOC in the same
  frame. 6111/11112 = 55.0%. The drive unit separately reports 55% in `32/00`.
* the torque sensor reports 1265 ADC counts in `31/00`; the drive unit reports
  1265 in `32/00`.
* `32/03` decodes to a 28" wheel at 2205 mm, inside the 1880--2510 mm the wheel
  table allows for that size, with a 25 km/h limit.

### The live fault code

`12/00` carries the fault the controller is showing, one byte, zero when there
is none. Nothing in either upstream project says so; it was settled by
capturing the same bike in two states.

| | faulty bike, 2026-08-17 | bench after repair, 2026-08-18 |
| --- | --- | --- |
| `02FF1200` drive unit `12/00` | `07` | `00` |
| `03FF1300` display `13/00` | `07` | `00` |
| what the display was showing | error 07, assist disabled | no fault |

This corrects something recorded earlier in this document. The overvoltage case
below says that this firmware offers "no stored fault to clear over CAN". The
*drive unit* will not answer a `60/07` read, which is what that was based on.
The *live* code is broadcast about once a second and needs no request at all,
so it is readable in listen-only mode, and `monitor --passive` now names it.

But the stored log was there all along, on the **display**. `DP C340.C` answers
`60/07` with the history as ASCII digit pairs, and on this bike it holds:

```
code 7   Over voltage protection
code 36  Keypad detection circuit error
```

Code 7 is the fault the whole overvoltage investigation below was about. The
tool asked the drive unit, got nothing, and reported no readable fault log --
so `errors` and `diagnose` now ask the drive unit *and* the display, and say
which one answered. Note what a display-held log means: a display can outlive
several controllers, so an entry in it does not prove the motor currently
fitted ever had that fault.

Worth stating plainly what that costs when it is missed. Replaying the original
capture through the current tool prints:

```
! error 7: Over voltage protection
  Check battery and charger compatibility, inspect battery, discharge if overcharged
! controller reports 51.60 V but the battery reports 37.48 V, a factor of 1.377.
```

Both lines were derivable from a 15-second passive capture on day one. The
description of code 7 was vendored in this repository the whole time, in
`bafang_canable_pro/ui/js/shared.js`; this tool exposed only the three codes
`OpenBafangTool` carries and reported the other twenty-four, code 7 among them,
as "no description available".

### What the battery's absence changed

A second capture with the battery disconnected and the harness on a bench
supply -- torque sensor and display only -- separates battery-driven traffic
from the rest, and shakes several constants loose. 159 frames/s against 166
with the battery present.

| message | with battery | bench, no battery | reading |
| --- | --- | --- | --- |
| `04F834xx`, `041A6401` | 34 frames | **gone** | all battery-sourced traffic, as expected |
| `03216400` | not sent | 202 frames, unanswered | the display asks for `BatteryDesign` forever when nothing answers; with a battery it asks once and stops |
| `03216401` | 22 frames | 202 frames, unanswered | it keeps polling into the void either way |
| `02F83207` | 7 zero bytes | bytes 5--6 live, 1626--1689 | so it is not an error block, and not static either |
| `02F83208` | `0000` | `0000`, twice `3500`/`4000` | live, mostly idle |
| `02F83000` | not seen | `11000000`, `12000000`, twice | read at the time as a start-up announcement. **Wrong** -- it is a free-running uptime counter, and two samples ten seconds apart cannot tell the two apart. See below |
| `03106300` | `55 15 00 01` | `55 15 01 01` | byte 2 moved. Byte 1 has separately been seen as `0B`, so at least two of these four bytes are live |
| `02F83201` voltage | 51.50 V | 40.10--40.20 V, +-0.10 | the repaired sense path, tracking a bench supply instead of reading 1.363x high |

The torque cross-check survives the change of conditions, which is the point of
repeating it: the sensor reported 1328--1351 counts and the drive unit
1332--1343 over the same window, on a bike whose idle sat at 1257--1269 the day
before.

### Turning the output shaft

Three bench captures with the shaft driven: by hand for about one revolution,
by a drill labelled 550 rpm for nineteen seconds, and by hand again at a steady
88--89 rpm for twenty-nine. The last one settles both open questions.

**`32/07` bytes 5--6 count the output shaft, 64 counts per revolution.**
Monotonic while it runs -- not one backwards step in 3983 frames -- and it
stops the moment the shaft does.

It is a **trip counter, not an odometer**. It restarted from 10833 and from
1689 during a single afternoon, and it read exactly 0 through both captures of
the bike, whose motor had no shaft fitted at the time and so had never turned
it. A restart is not a wrap and must not be read as one: 10833 to 158 taken as
a wrap is 857 revolutions inside one 96 ms broadcast. Over 23 s of steady rotation the counter advanced at
94.46 counts/s against a cadence the sensor held at 88--89 rpm, giving 63.68
counts per revolution; shorter windows inside it give 63.65 and 63.69.

The first attempt at this put it at 60, from the drill, whose implied rate came
out at 552 against a 550 label. The drill was the weaker reference: those
labels are no-load figures, and at 64 counts per revolution that run works out
to 518 rpm, 94% of the label, which is ordinary for a drill under load. The
cadence byte is the better one -- the firmware uses it for its own assist
decisions, it held to +-0.5 rpm for the whole window, and `32/00` byte 3 agrees
with it exactly. Taking it as true rpm puts the count between 63.7 and 64.4,
and 64 is the sort of number an encoder actually has.

**Both cadence bytes are plain rpm.** Measured across 4507 paired samples at
25--150 rpm:

| | median ratio |
| --- | --- |
| `31/00` byte 2 / true rpm | **1.004** |
| `32/00` byte 3 / true rpm | 1.004 |
| `32/00` byte 3 / `31/00` byte 2 | **1.000** |

The two nodes report the identical number, and it is the shaft's rpm. Both
vendored projects read this byte directly as rpm and both are right.

An earlier version of this document reported the drive unit's byte as
*twice* the sensor's, from two samples taken during a hand turn of a single
revolution. That was wrong. The capture it came from was about one revolution
long, sampled at 10 Hz, and carried the timestamp faults described in
`hardware.md`; the ratio it produced -- median 1.85, spread 1.60 to 2.53 -- was
noise around 1.0 with a fat tail, not a factor of two. Nothing was changed in
the codecs on the strength of it, which is the only reason the error cost
nothing but a paragraph.

**Above about 450 rpm the cadence bytes stop meaning anything.** The drill run
had them reading 16 or 23 at a steady 518 rpm, and during spin-down through
420, 383 and 224 rpm they read 201, 165 and 97 -- higher at a third of the
speed. Nothing is wrong with the sensor: it is a pedal cadence sensor being
spun five times faster than a rider ever would. This is what makes `32/07`
worth having, since it stays linear at any rate.

**`32/08` is not a speed field.** It goes non-zero only while the shaft turns,
which is why it first looked like one, but through nineteen seconds of constant
speed it decayed steadily from 186 to about 98 and then flattened. Something
settling or warming, sampled while the shaft happens to be moving.

The torque channel remains completely unexercised: a freely spun shaft loads
nothing, so the sensor's torque reading stayed inside the same band it occupies
at rest.

### The display's 63/00

`03106300` is the display talking to the drive unit, four bytes at about 10 Hz,
so it is readable in listen-only mode. Fully decoded now, by stepping a
`DP C340.CAN` from assist 5 down to walk assist one press at a time and then
holding `+` to switch the lamp on.

| byte | meaning |
| --- | --- |
| 0 low nibble | how many assist levels the display is configured for -- `0x55 & 0x0F` = 5 |
| 0 bit 5 | boost |
| 1 | current assist level, as a **lookup code, not a number** |
| 2 bit 0 | lamp |
| 2 bit 1 | `+` button held |
| 2 bit 5 | `-` button held |

The level codes are the surprise. They are a table, and not a monotonic one:
level 5 is `3`, which is numerically lower than level 1's `11`. Stepping down
one press at a time produced exactly this, in this order:

| level | 5 | 4 | 3 | 2 | 1 | 0 | walk |
| --- | --- | --- | --- | --- | --- | --- | --- |
| code | `0x03` | `0x17` | `0x15` | `0x0D` | `0x0B` | `0x00` | `0x06` |

That matches `bafang_canable_pro`'s table for a five-level display exactly, and
is why an earlier capture -- pressing up and down quickly, without knowing what
the display showed -- looked like a bitfield with gaps of 8, 2, 8, 2. It was
never arithmetic. The table is per-display; only the 3-, 5- and 9-level
configurations are known, and any other count reports the raw code rather than
guessing.

Switching the lamp on walked byte 2 through `00`, `02`, `03`, `01`: button
pressed, then lamp on with the button still held, then lamp on with it
released. Both bits behave independently, as the vendor layout says.

### The torque channel responds

The first capture in which the torque path moved at all. Both cranks fitted,
force applied by hand without turning -- cadence stayed 0 throughout.

| | `31/00` torque |
| --- | --- |
| at rest (first four seconds) | 1332, holding to +-3 |
| under hand force (next fifteen) | 1285--1328 |

So about **47 counts of usable travel below the resting value**, and only
below it: nothing pushed the reading up. Whether that is the sign convention
or simply which way the freewheel resists is not settled here.

`ControllerRealtime0`'s torque field tracks it exactly, sample for sample --
1332 at rest, 1296 at the deepest, 1316 and 1300 in between -- so that
cross-check holds under load as well as at idle.

The resting value tracks the mechanical assembly, not the day. It sat at
1261--1269 across both captures of the motor **with no shaft fitted**, and at
1316--1339 across every bench capture **with the shaft in**. Those are two
stable states about 70 counts apart, not drift. Anything derived from this
field still needs a baseline taken from the machine in front of you, but that
baseline holds while the machine does.

`31/01`, `31/02` and `31/03` did not move by a single byte under load, which
settles what they are not: whatever they hold, it is not strain.

### What a bench without a turnable motor cannot show

A Bafang mid-drive has a freewheel between the motor and the output, so turning
the output shaft does not back-drive the rotor. On the bench used here the motor
cannot be turned at all, and that shapes what the captures above do and do not
establish.

It *helps* in one way. Both cadence figures -- the torque sensor's `31/00`
byte 2 and the drive unit's `32/00` byte 3 -- went non-zero together while the
rotor stayed still, so both are measuring the crank/output side and nothing
else. The factor of two between them is therefore a genuine scale difference
between two readings of one shaft, not an artifact of two nodes watching
different parts of the drivetrain. It also constrains `32/07`: that accumulator
advanced with the rotor stationary, so whatever it counts, it is not motor
revolutions.

It *limits* the rest. Motor speed, phase current, hall-sensor state and back-EMF
cannot be exercised, so any field carrying them stays zero here and its
stillness proves nothing. `32/01`'s current field was 0 throughout, as expected.

And rotation is not the same experiment as load. Spinning a freewheeling output
applies no torque: across the rotation the sensor's torque reading spanned 11
counts, *less* than the 23 counts it spanned at rest. The torque path is
completely unexercised by these captures. Moving those fields needs force
against resistance -- holding the shaft and pushing -- which is a different
action from turning it.

### One that does not, and why

The drive unit reports 51.50 V in `32/01` while the battery reports 37.47 V in
`34/01` -- a factor of 1.374. That is not a decoding error. It is the
voltage-sense gain fault worked through in
[the case below](#diagnosing-an-overvoltage-fault-a-worked-case), and the
codecs were reading the right bytes throughout.

### The uptime counter, and using it to check a capture's clock

`30/00` is four bytes little-endian, counting ticks of the drive unit's own
clock since it powered on. It was first read as a start-up announcement, from
two samples in one capture -- which is exactly what a counter broadcast every
ten seconds looks like if you only watch it for twenty seconds. Eleven captures
across two days say otherwise: it increments by one every 10.023 to 10.028 s
and reaches at least 0x35 (53 ticks, nearly nine minutes) without stopping.

The tick is nominally 10 s. The 0.26% excess is this drive unit's clock running
slow, and `codecs.UPTIME_TICK_SECONDS` carries the measured figure rather than
the intended one, because 10.0 misplaces a boot instant by a second for every
six and a half minutes of uptime.

It resets on every power cycle, so it is not an hour meter and says nothing
about the life of the motor. What it gives you is the one thing no other
message on this bus carries: **an absolute reference for when the system under
observation was switched on**. Subtract `seconds` from the timestamp of the
frame and you have the power-on instant. Two captures of one power cycle must
agree on it.

That makes it an integrity check on the capture's own clock that does not
depend on the host at all. Four captures taken between 12:42 and 12:51 one
afternoon:

| capture | tick | reconstructed power-on |
| --- | --- | --- |
| `bench-slowspin` | 1 | 12:42:22 |
| `bench-slowspin2` | 26 | 12:42:26 |
| `bench-slowspin3` | 38 | 12:42:25 |
| `bench-cadence` | 53 | 12:42:25 |

Four independent recordings spanning nine minutes, landing within 5.5 s of each
other -- and 5.5 s is the counter's own resolution, since where inside a tick a
capture began is not observable. `bench-assist` and `bench-verify`, four
minutes apart, likewise both reconstruct 11:58:1x.

`bench-validate` reconstructs **17:37**, nearly six hours from when it was
taken. That capture is the one with the frozen-clock fault described in
[docs/hardware.md](hardware.md); the counter catches it without knowing
anything about slcan, gs\_usb or buffer drains.

### What the bus does at power-on, and the question of a locked firmware

One capture, `bench-assist`, begins with `30/00` at zero, so it is the only
recording that covers the drive unit actually coming up. What the display does
there is the only identity exchange anywhere in 42000 captured frames:

```
DISPLAY -> DRIVE_UNIT   READ_CMD  60/03    x92, in five bursts
DRIVE_UNIT -> DISPLAY   multiframe answer  x5, 29 bytes: CRX210.350.FC1.0A47F5WC160200
DISPLAY -> DRIVE_UNIT   NORMAL_ACK 60/03   x5
```

then it stops, and does not ask again for the remaining 1759 frames of that
capture or in any of the ten other captures, none of which start from a cold
drive unit. So: **at power-on the display reads the drive unit's serial number,
retries until it gets it, acknowledges it, and never asks again.**

That is the shape of a pairing check. It is equally the shape of a display
reading a part number so it can show it in a menu, and one bike with one
display cannot tell those apart. What can be said is what is *not* there:

* No challenge, no nonce, no response that depends on a previous frame. Every
  payload in every capture is a plain scaled integer or an ASCII part number.
* Nothing on the bus is high-entropy. A rolling code would stand out
  immediately against traffic this repetitive.
* The battery is read, never challenged -- `64/00` and `64/01` are ordinary
  data polls, and the display sends them into the void forever when no battery
  answers rather than faulting.
* The drive unit, torque sensor and display run normally with **no battery at
  all** on the bench, reporting no fault. There is no gate that requires a
  particular pack to be present.
* The assist-level encoding is Bafang's own five-level lookup table, matching
  `bafang_canable_pro` exactly (see [above](#the-displays-6300)), not a
  re-mapped OEM variant.
* The fault codes are the generic Bafang table. This unit's code 7 is
  "over voltage protection" in `bafang_canable_pro`'s list, and it meant
  exactly that.
* The model string `CR X210.350.FC` is a stock Bafang part number.

Neither vendored project implements or mentions any pairing, serial matching or
authentication, and neither carries a fault code for a mismatched component.

The experiment that would settle it is a boot capture with a **different**
display or drive unit on the bus, and watching whether `60/03` gets asked more
than five times or whether a fault appears. Until someone does that, the honest
position is: nothing observed suggests a cryptographic lock, and one boot-time
serial read is unexplained.

The practical constraint on replacing a part is a different one, and it is
real. This firmware answers identity reads only -- 5 of 16 known commands, no
parameter block, from any source id (see [the top of this
document](#what-is-known-and-what-is-not)). Wheel size, speed limit and the
assist-level currents cannot be read or written over CAN here. A replacement
part therefore has to arrive already configured correctly, because this tool
cannot configure it on this firmware, whatever the protocol permits in general.

### The one block that does answer

The drive unit hands over no parameter block, but the display answers `63/01`:

```
76 01 00 A3 0E 00 56 03
  total    374 km
  trip     374.7 km
  max      85.4 km/h
```

A never-reset trip sitting a fraction above a whole-kilometre total is what the
two scalings predict, which is the layout checking itself. `max_speed` is a
latched high-water mark and 85.4 km/h is not something a 25 km/h EPAC pedals
to -- one spurious speed-sensor sample sets it permanently, so read it as a
property of the sensor rather than of the bike.

Both `DisplayData1` and `DisplayData2` had decoders and differential tests
against the vendored JavaScript from the start, and **nothing in this tool ever
asked a device for them**. A readable odometer sat unreachable behind a codec
already proven correct. `diagnose` now reads both; `63/02` is silent on this
display, so a partial answer is the normal result.

The `DP C340.C` has no configuration menu at all -- its only control is a view
toggle that cycles odometer, trip, average speed and maximum speed on the
screen. That makes it a better check on this block than a settings menu would
have been: **the display shows three of these four numbers, so they can be read
off the screen and compared against the decode directly.** If the screen agrees
with 374 km / 374.7 km / 85.4 km/h, the layout is confirmed from outside the
protocol entirely. If the maximum reads as something else, the field is wrong
and the "latched high-water mark" reading of 85.4 km/h goes with it.

Note the asymmetry worth chasing: the screen displays an average speed, and the
display refuses to answer `63/02`, which is where both vendored parsers put
average speed. Either it is computed on the display and never exposed, or it
lives somewhere this tool has not looked.

### Configuring what cannot be read

`32/03` is the one place the two halves of this firmware's behaviour meet.
The drive unit **will not answer** a `32/03` read -- and it **broadcasts**
`32/03` every two seconds, and the write command for wheel size and speed
limit is that same `32/03`. So the current values are on the wire even though
the read is unavailable, and the way to change them is available too.

`wheel` was nevertheless unusable here, because it began with
`read_speed_parameters()` and gave up when that timed out. It now falls back to
the broadcast, which means the firmware that hands over no parameter block at
all is still configurable for the two settings that matter most when a part is
replaced.

#### Measured, on the bike

That was reasoning about a write nobody had performed. It has now been
performed. Circumference 2205 -> 2206 mm, confirmed, and put straight back:

```
   +0.000s  TOOL->DRIVE_UNIT       WRITE_CMD   32/03  c409c0019e08
   +0.005s  DRIVE_UNIT->TOOL       NORMAL_ACK  32/03
   +0.304s  DRIVE_UNIT->BROADCAST  WRITE_CMD   32/03  c409c0019e08
```

**The drive unit acknowledges the write in 5 ms and puts the new value on its
own broadcast 300 ms later.** It answered a read of that same code 0 times out
of 10.

Three things follow.

**Reads and writes are separate handlers, and probing one says nothing about
the other.** `capabilities()` only ever sends `READ_CMD`, so every "silent" in
this document is a statement about the read side alone. `32/03` is silent to a
read and fully functional to a write. Any conclusion here of the form "this
firmware does not implement X" should be read as "does not answer a read of X".

**The drive unit does acknowledge writes.** No `NORMAL_ACK` from the drive unit
appears anywhere in 13,000 captured frames, which had looked like a firmware
that never acknowledges anything. It is simpler than that: nothing had ever
written to it. The display's `63/00` and `63/03` writes go unacknowledged, so
the behaviour is per-command rather than absent.

**The broadcast is the verification.** `write_speed_parameters` now waits for
the value to appear on `32/03` before reporting success, and raises if it does
not. Previously it reported success on the acknowledgement alone -- and an
acknowledgement only says the frame was accepted, not that the setting took.
For a command that changes how fast a bike may go, that gap was worth closing.
The broadcast is in fact better evidence than a read-back would be: it is what
the drive unit tells the rest of the bike, not what it tells the tool that just
wrote to it.

This also matches what owners report about fitting a generic Bafang display:
that it can set speed limit and wheel size on a bike whose own display cannot.
A display setting those values is writing `32/03`; it never needed to read it.

**A speed limit is a legal setting**, and above the local EPAC figure the
vehicle stops being a bicycle in most of Europe. `profiles/m200.py` flags
values outside its limits and `--force` overrides that, as it does everywhere
else in this tool. What the law where you ride allows is your call, not this
tool's.

### What the DP C340.C menu exposes

Five items, and they are worth listing because three of them drive fields on
the bus to known values -- which is otherwise very hard to arrange on a system
that answers almost nothing:

The vehicle manual (eGoing/Crescent Center, 2022-11-17) documents all of them:

| item | what it is | what it reaches |
| --- | --- | --- |
| wheel size | **"locked to 28\""** | `32/03` bytes 2--3. The menu will not change it |
| speed | **"locked to 25 km/h"** | `32/03` bytes 0--1. The menu will not change it |
| assist levels | **"locked to 5 levels"** | `63/00` byte 0 low nibble, which does read 5 |
| `CL` | clear trip meter | shows `374.7`, which is `63/01`'s trip **exactly** -- see below |
| `UN` | units, km/h or MPH | not yet located on the bus |
| `US` | USB port mode, Y or N | `Y` puts the **USB port** into dealer communication mode, `N` is ordinary charging. It unlocks nothing in the display's menu -- but it is the port a dealer's PC uses, and the only path from there to the motor is this CAN bus |
| software version | display firmware | `60/01`, which reads `DPC340CQ10201.2` |
| auto shutdown | 5 min default, adjustable 0--9 | `63/03`, which reads `05` |
| light sensor | 0--5, default 3 | `63/04` bytes 0--1 |
| backlight | 0--5, default 3 | `63/04` bytes 2--3 |

Two of those are worth pausing on.

**The lock is real, documented, and in the display -- not in the protocol.**
The manual says in plain words that wheel size, speed and assist levels are
locked on this bike. That is the brand deliberately restricting the vehicle,
exactly as one would suspect of an EPAC sold in the EU. But it is implemented
as a menu that declines to change them, and the same manual's numbers -- 28"
and 25 km/h -- are what `32/03` broadcasts unasked every two seconds, over a
protocol that accepts `32/03` writes and never once answered ERROR_ACK. The
restriction and the protocol are separate layers, and only the top one is
locked. That is also why fitting a generic Bafang display is reported to make
these settings adjustable again: the new display simply does not implement the
refusal.

**The manual doubles as a decode check.** It states the two values
independently of any protocol work, and decoding `C4 09 C0 01 9D 08` gives
25.0 km/h and a 28" wheel. Two documents sharing no code path agreeing on both
fields is a stronger confirmation than either upstream parser could give.

`CL` is the strongest confirmation on this page and it cost nothing. The
display's own menu shows the trip meter as **374.7**, and decoding `63/01`
bytes 3--5 as a 24-bit little-endian count of tenths gives **374.7 km**. That
is the device agreeing with the decode through its own screen, with no
protocol reasoning in between.

Do not use `CL` to test further. Clearing the trip would confirm that those
bytes go to zero, and it would destroy a 374.7 km trip reading to learn
something the screen has already shown.

### Riding style (korstil), and the two places it could live

The manual documents a **dealer-only** riding-style selector -- page 15,
"KORSTILSVALJARE (ENDAST ATERFORSALJARE)" -- with three settings shown on the
display as `D`, `S` and `C`: dynamisk, standard, kontroll. It changes how the
motor behaves and it is not in the user menu.

Two fields on the bus could carry it, and the captures cannot separate them:

| candidate | value seen | who reads it |
| --- | --- | --- |
| `63/00` byte 0 bit 4 | 1 | both vendored projects, as a **two**-state ride mode. `bafang_canable_pro` comments its own version "Simplified" |
| `63/00` byte 3 | `0x01` in 3567 of 3568 frames | **neither project reads this byte at all** |

The problem with the first is arithmetic: korstil has three states and one bit
holds two. Bits 4 and 5 together would hold four, but bit 5 is already spoken
for as `boost` in both projects. The attraction of the second is that byte 3
is unclaimed, constant, and sits at 1 -- the middle of a 0/1/2 encoding, which
is where a bike left at standard would sit.

And that is exactly the trouble: **a three-state setting at its middle value
reads 1 in either place.** Both currently show 1. No amount of re-reading the
existing captures separates them.

#### Narrowing it by elimination

Everything the display has ever sent the drive unit, across all captures:

| | | |
| --- | --- | --- |
| `WRITE_CMD` | `63/00` | 3568 |
| `WRITE_CMD` | `63/03` | 325 |
| `READ_CMD` | `60/03` | 258 |
| `READ_CMD` | `60/01` | 1 |

That list carries the argument:

1. The display **shows** the riding style, as `D`, `S` or `C`.
2. The display **never reads a parameter block** from the drive unit -- it only
   ever asks for the serial number and the software version. So it is not
   learning the setting from the controller.
3. Therefore the display holds it.
4. The manual says the setting changes how the **motor** behaves, so the
   controller has to be told.
5. The only things the display sends the controller are `63/00` and `63/03`.
6. `63/03` is one byte reading `05`, and the manual documents this display's
   auto-shutdown as five minutes. That byte is accounted for.

Which leaves `63/00`. Within it, bit 4 cannot hold three states and is already
read as a two-state field by both projects, while byte 3 is unclaimed, constant
and sitting at 1.

**So byte 3 is the strong candidate.** Every step above is evidenced, but it is
still an elimination rather than an observation -- the setting has never been
seen to change. The tool carries both: `ride_mode` as an integer rather than a
bool, so a third state appearing there stays visible instead of being
flattened, and `mode_byte` passed through raw.

#### What a third source does to that argument

`OpenSourceEBike/Bafang_M500_M600` labels `63/00` byte 3 **boost mode**, off =
`01` and on = `00`. That is a direct claim on the byte the elimination above
called unclaimed, and it has to be taken seriously rather than argued away.

It is not, however, a stronger claim than ours. The same page says the byte
"is always 1 with my DPC080 display" -- so its author never watched it change
either. Byte 3 is now **disputed rather than unclaimed**, which weakens the
elimination without killing it: the argument that the display must tell the
controller something, and that `63/00` and `63/03` are the only channels it
has, is untouched.

The comparison also turns up a third possibility that no source covers. On
that DPC080 byte 0 reads `0x05`. On this `DP C340.C` it reads `0x55` in every
frame after boot:

| | byte 0 | low nibble | high nibble |
| --- | --- | --- | --- |
| DPC080 (M500, published) | `0x05` | 5 -- five assist levels | `0x0` |
| DP C340.C (this bike) | `0x55` | 5 -- five assist levels | `0x5` |

Both vendored parsers take the low nibble as the level count and then read
bits 4 and 5 of the high nibble as `ride_mode` and `boost`. But `0x5` in the
high nibble also sets **bit 6, which nothing reads**, and it makes the high
nibble equal the low one. So `ride_mode = 1` and `boost = false` on this bike
may be nothing more than two bits sliced out of a nibble that is not a set of
independent flags. `byte0` is now carried raw so that stays visible.

There is also one frame in every capture that breaks the byte-3 pattern, and
it is worth naming so nobody mistakes it for the setting moving. Of 3568
frames, 3567 read `55 xx xx 01`; the exception is `05 0B 00 00`, the display's
very first frame after power-on, three milliseconds before it starts asking
for software versions. Byte 0 is uninitialised in it too. It is a boot
artifact.

**The experiment is to change the setting and capture across the change.** One
capture, any two of the three positions, and the byte that moves settles it.

`US` is not the way in. It sounds like a service unlock and is not one: the
manual describes it as switching the **USB port** between charging and
communication with a computer -- "KOMMUNIKATION VIA USB-PORT, endast for
aterforsaljare" -- so `Y` repurposes the port for a dealer's PC rather than
opening anything in the display's own menu.

What that does imply is worth noting: the dealer's PC reaches the bike through
that port, and the only link from the display to the drive unit is this CAN
bus. So a dealer changing the riding style has to put the change on the wire
we are already able to sniff.

Note what this is not. Riding style changes assist behaviour within the
limits; it is not the speed limit, which is `32/03` and is a separate setting
this document covers above.

### Is the silence itself the lock?

The obvious next thought: an unmodified Bafang M200 would answer parameter
reads, and this one does not because the brand blocked them to stop
derestriction. The bike is a Swedish EPAC and the speed limit it broadcasts is
exactly the regulated 25 km/h, so the motive is real.

Two observations pull toward it:

* **The firmware computes the payloads it will not hand over.** `probe` reports
  `ControllerRealtime0`, `ControllerRealtime1` and `SensorRealtime` as
  unsupported, and all three arrive as broadcasts continuously, in the byte
  layout the read command would have returned. The data is not missing. Only
  the request path is.
* **The service layer works.** The drive unit answers `60/03` as a five-frame
  multiframe transfer, so the machinery a 64-byte parameter block needs is
  present and running.

Three pull against it:

* **The shape is wrong for a regulatory measure.** Derestriction is a *write*
  problem. Blocking a *read* of speed, torque, cadence and controller
  temperature accomplishes nothing regulatory, and those values are shouted on
  the same bus unasked several times a second. Refusing to answer a question
  whose answer you are already broadcasting is not a lock; it is a missing
  handler.
* **The regulated values themselves are broadcast in the clear.** `32/03`
  carries the wheel circumference and the 25 km/h limit unasked. Anyone hiding
  the tuning surface would hide that first.
* **Nothing says an M200 ever answered.** Neither upstream project lists it as
  tested hardware; both target the M500/M600 generation. "This generation's CAN
  service handler implements identity and little else" needs no conspiracy.

None of that settles it, and the bus can. **ERROR_ACK and silence are different
claims.** A firmware that replies ERROR_ACK to `60/11` has a handler for it and
is declining. A firmware that says nothing has no handler. Until this was
written `capabilities()` caught both as one exception and reported `false`, so
the tool had been discarding the only evidence that bears on the question.

`probe` now reports `answered`, `refused` or `silent` per command, and probes
one unassigned code on the same page (`60/7F`) as a control, so the silent case
has a measured baseline instead of an assumed one:

```bash
bafang-can probe
```

| what comes back | what it means |
| --- | --- |
| `Parameter1` refused, control silent | the firmware has a handler for it and says no. That is a lock |
| `Parameter1` silent, control silent | indistinguishable from a command this firmware never had |
| both refused | this firmware ERROR_ACKs anything unknown; the test is uninformative and `probe` says so rather than inventing a finding |

### The answer, measured

Run on 2026-08-18 against the reassembled bike, all three nodes:

| node | answered | refused | silent | control |
| --- | --- | --- | --- | --- |
| `CR X210.350.FC` drive unit | 5/16 | **0** | 11 | silent |
| `SR PA450.32.ST.C` sensor | 5/6 | **0** | 1 | silent |
| `DP C340.C` display | 7/12 | **0** | 5 | silent |

**Not one ERROR_ACK on the whole bus.** Every unanswered command behaves
exactly like `60/7F`, a code that does not exist. Nothing here is refusing;
nothing answers.

The torque sensor is what makes this more than one data point. It is a separate
product from a separate line, it has no tuning surface worth locking, and it
behaves identically: identity reads answer, `31/00` is silent, no refusals --
while broadcasting `31/00` continuously the entire time. Whatever explains the
drive unit explains the sensor too, and "the brand blocked derestriction" does
not explain a torque sensor.

The display is the third: seven commands answer, including `63/01` and the
stored fault log, and five are silent, again with no refusals. Three devices
from three product lines, one pattern.

So the honest reading is: **this protocol generation implements a narrow pull
interface and pushes everything else as broadcasts.** The missing commands look
absent, not blocked. That is not proof -- a lock implemented by deleting the
handler outright is indistinguishable from a handler that was never written,
and no measurement on this bus can separate those. What can be said is that the
one signature a *selective* block would leave is not there.

The claim to avoid is the confident one in either direction. Comparing against
an M200 on a bike from a different brand would settle it; nothing on this bench
can.

**The vehicle manual then settled the question that actually mattered**, from a
direction no amount of bus probing would have reached. It states that this
bike's wheel size, speed and assist levels are *locked* -- so the brand did
deliberately restrict the vehicle. The restriction is in the display's menu,
which declines to change them, and not in the CAN protocol, which broadcasts
those values unasked, accepts writes to them, and refuses nothing. See
[the menu section](#what-the-dp-c340c-menu-exposes). Both readings of the
evidence were right about different layers.

### Cross-referencing the M500/M600 work

Everything above was decoded from the two vendored projects plus this bike.
That is two sources, and both are reimplementations by the same small
community, so agreement between them is worth less than it looks. This is what
a search outside them turned up and what it did and did not change.

Three sources were found and read:

| source | what it actually is | weight |
| --- | --- | --- |
| [`OpenSourceEBike/Bafang_M500_M600`](https://github.com/OpenSourceEBike/Bafang_M500_M600) | the command table extracted from the **BESST desktop application's own JavaScript**, plus PCAN logs of an M500 powering up and down, plus a parameter-block map for `60/11`, `60/12`, `60/17` and `60/18` | highest available. The command names and codes are Bafang's, not a guess |
| [`strnk/varstrom-usb-can`](https://github.com/strnk/varstrom-usb-can) | the serial protocol of a third-party programming cable, with a trace of what its software reads and writes | independent, small, and confirms one thing we had only from `bafang_canable_pro` |
| [`kaspars.net/blog/bafang-canbus`](https://kaspars.net/blog/bafang-canbus) | a short write-up of the identifier format and `32/03` | derivative of the first, but arrives at the same `32/03` layout separately |

The BESST bundle was fetched and grepped directly rather than trusted
second-hand. `bart594/bafang_canable_pro` is the upstream of the vendored
`mdi-9` fork and is a year behind it, so nothing is missing there.

#### What it confirms

* **`62/D9` is the startup angle.** `bafang_canable_pro` names it that and this
  project carried the name on its authority alone. The Varstrom trace shows a
  completely different tool reading and writing the same two bytes in the same
  place in a "read all", which is as close to independent corroboration as this
  gets.
* **`31/00` byte 3 is a rolling counter.** Found here by watching a G210 and
  used by `quality` to detect dropped frames. A 333-frame M500 shutdown log
  shows bytes 0--2 frozen while byte 3 advances by one per frame through a full
  wrap. Their table calls it "Progressive", which is the same fact named
  vaguely.
* **`63/03` is minutes of idle before shutdown, and the display *writes* it.**
  The M500 power-on log has the display sending `03106303` with one byte `05`
  as its tenth frame and repeating it about once a second. This bike's display
  does exactly the same. That closes a question this document had left open --
  whether `63/03` was a value held by the display or pushed to the controller.
* **The power-on handshake.** Our `session-2026-08-18-1502` capture and their
  2021 M500 log open with the same sequence: `63/00`, then software version,
  then `64/00` and `64/01` at the battery. Two displays four years and one
  motor generation apart, byte for byte.

#### What it adds

Sixteen command codes that neither vendored project implements, taken from
Bafang's own software. They are now in `commands.py` so that `probe` asks this
bike about each one:

| code | BESST name |
| --- | --- |
| `60/06` | `params` |
| `60/13`--`60/16` | `conParams_3`..`conParams_6` |
| `61/00` | `sensorCalibration` (read) |
| `62/15` | `controllerFeatures` |
| `36/00`--`36/03` | `transmissionInformation` |
| `37/00` | `eletronicLockInformation` (sic) |
| `64/06`--`64/09` | `batteryCellsInformation_4`..`_7` |
| `64/15` | `batteryCharacteristics` |

**No payload layout is claimed for any of them**, and none is decoded. The
codes are the reliable part; which device answers them is inferred from what
BESST addresses.

#### Probing them against the bike

All sixteen were then read from a live G210. Fifteen are silent -- including
`62/15 controllerFeatures`, the one that would have mattered most for the lock
question. **One is not.**

`60/06` answers. Not with data, and not with a refusal: with a properly formed
transfer declaring a length of zero.

```
read  60/06 ->  MULTIFRAME_START 60/06 dlc=1 00      length byte = 0
                MULTIFRAME_END   00/00 dlc=0         nothing follows

read  60/03 ->  MULTIFRAME_START 60/03 dlc=1 1d      length byte = 29
                MULTIFRAME       00/00 dlc=8 4352583231302e33
                ...
```

Side by side with the serial number the difference is unmistakable. The
handler is there, it ran, and it declared that it has nothing. Every
parameter-block code on the same page -- `60/10` through `60/18` -- is silent.

This is a **fourth probe outcome**, and it had been collapsing into
"answered". `capabilities()` now reports `empty` separately, because calling
it "answered" implies a value that was never sent and calling it "silent"
denies a handler that demonstrably ran. The display does it too, on
`60/04 CustomerNumber`.

What it does *not* do is reopen the lock question. An empty `params` is a
handler with nothing behind it, which is a weaker thing than a handler that
declines. Across every node the count of ERROR_ACKs is still zero.

The parameter-block map for `60/11`/`60/12`/`60/17`/`60/18` is the other
substantial addition and is not yet reconciled with `codecs.py` -- their field
list is per-byte and considerably more detailed than what either vendored
project exposes, including the nine per-level current and speed limits and a
`60/18` block of two speed/current limit pairs that reads like the EPAC
compliance surface. That is a separate piece of work, and it wants a real
`60/11` payload from this bike to check against; this firmware refuses to give
one.

#### The display drops requests, and it took a wrong answer to notice

The first probe run after the command table grew reported this display's
`ErrorCode` and `SoftwareVersion` as **silent**. Both answer. Reading them
directly, one at a time, worked immediately.

That is the probe's worst possible failure. "Silent" is the reading that says
a firmware never implemented a command, and the entire lock argument is built
on counting silences against refusals. A probe that invents silences is a
probe that can invent a locked firmware.

Ten attempts at each command, on the bike, separate two populations with no
overlap between them:

| node | commands it implements | commands it lacks |
| --- | --- | --- |
| drive unit | 10 of 10, every time | 0 of 10, every time |
| display `DP C340.C` | **6 to 9 of 10** | 0 of 10, every time |

The drive unit is deterministic. The display is not -- `ModelNumber` answered
6 times in 10, `SoftwareVersion` 7, `HardwareVersion` 9 -- while the commands
it genuinely lacks (`Manufacturer`, `BootloaderVersion`, `DisplayRealtime`,
`63/03`, `63/04`) answered 0 of 10 without exception. So the two categories
never actually blur; the display simply has to be asked more than once before
its silence carries any information.

The likely reason is contention rather than anything deliberate. The display
is the busiest talker on this bus: `63/00` every 100 ms plus two battery polls
in the same breath, against a torque sensor broadcasting every 11 ms. A
service request that loses arbitration is not retried by the display.

Separately, and more important than the loss rate: this probe **only sends
reads**. See "Configuring what cannot be read" -- `32/03` is silent to a read
and accepts writes normally. Every "silent" recorded in this document is a
statement about the read side alone.

`capabilities()` now makes six attempts before reporting silence, and only on
commands about to be called absent. Six because it was measured: at the worst
observed rate a single attempt is wrong 40% of the time, three attempts 6%,
six attempts under 1%. Refusals and answers are not retried -- both are
positive evidence and arrive first time.

**Two things follow for anything already recorded here.** Any earlier claim
that this display lacks a command rests on one attempt and should be re-probed
before it is trusted. And the reverse never applies: an answer is proof, so
nothing previously reported as present is in doubt.

#### What it contradicts

**`12/00`.** This document reads it as the live fault code, on the evidence
that it held `07` while the bike displayed error 07 and `00` after the repair,
with the display echoing it on `13/00`. `OpenSourceEBike` reads it as a
bitfield: bit 0 brake, bit 1 motor stopped, bit 2 undervoltage. The two agree
that zero is healthy and cannot both be right above that.

Neither source is clearly stronger -- theirs is a label with no stated
experiment, and their own sample `0x11` sets a bit 4 their three-bit layout
does not explain; ours is one bike, one fault, one repair. The tool keeps the
fault-code reading and `codecs.ControllerState` records the dispute.

**The discriminator is one capture and nobody has run it: squeeze the brake
lever.** Under the bitfield reading a healthy bike goes to `0x01`; under the
fault-code reading it stays `00`, because 1 is not a fault code.

#### What it does not answer

* Nothing anywhere describes a **riding style** setting. The BESST bundle has
  no `ridingMode`, `sportMode` or equivalent identifier in 16 MB of source. So
  körstil is not a BESST-configurable parameter, which is consistent with it
  living in the display -- and leaves the byte still unidentified.
* `32/08`, `12/02`, `13/00` and `31/01`--`31/03` appear in no published table.
* `32/02`, `32/04`, `32/05` and `34/02` gain names and nothing else.
* Broadcast periods are only partly portable. `63/00` matches exactly -- 100 ms
  on their M500 and 100 ms here -- but `32/03` is 450 ms there and 2.004 s
  here. Their published rates are a starting guess for a new bus, not a
  specification, and this project's own measurements stay authoritative for
  the M200.

## What a road ride shows that a bench cannot

Everything above this line was measured with the bike on a stand, off a bench
supply, or with the wheel in the air. On 2026-08-20 the same G210 was recorded
for 102 s on the road, pack fitted, in passive mode through the candleLight
2.5: 16807 frames, 0 to 26.6 km/h, peak 15.1 A.

Start with what did *not* happen. No lost broadcasts, no duplicates, no
impossible timestamps -- the torque sensor's counter runs unbroken through all
8808 of its frames. The gs_usb receive path holds up at road speed with a motor
pulling 15 A a metre from the wiring, which is not something a bench capture
can establish.

Three excerpts of that ride are in `tests/data`, and each one settles something.

### The bus fails when the motor pulls

Eight frames in the ride carry the identifier `20000080`. They are not Bafang
frames and they are not corruption: they are **error frames**, the CAN
controller reporting that a frame on the wire was malformed. The tool used to
count them as corrupt identifiers under a comment blaming a resynchronising
slcan reader -- and this capture came off a gs_usb adapter, which has no serial
framing to resynchronise.

They are not scattered through the ride. All eight land in 2.1 s:

```
 83.45  speed  7.5 km/h   I =  8.4 A   U = 35.5 V
 83.65  ERROR FRAME  0000000000000001
 84.20  speed  7.5 km/h   I = 14.9 A   U = 34.3 V
 84.56  ERROR FRAME  0000020000000001   frame format error
 84.70  ERROR FRAME  0000040000000001   bit stuffing error
 85.45  speed  5.5 km/h   I = 15.1 A   U = 34.2 V
 85.77  ERROR FRAME  0000000000000001
 86.20  speed  5.2 km/h   I =  0.0 A   U = 36.9 V   <- errors stop with the current
```

That is the highest current of the entire ride, with the pack sagging 3 V, and
the errors stop the instant the current does. Motor switching noise coupling
into the bus, measured rather than assumed.

Three things follow. **These frames are worth keeping**: nothing else in the
capture points at the motor -- the drive unit reports no fault, no counter
skips, every node keeps broadcasting. **A frame destroyed this way can never
appear as loss**, because it never reaches a recorder to be missed; the error
frame is the only trace it leaves. And **the error class does not survive a
candump log**: python-can's `CanutilsLogWriter` stamps every error frame with
`CAN_ERR_FLAG | CAN_ERR_BUSERROR` whatever the controller actually said, so
offline the class reads as unknown and only the payload detail survives. Live,
the class bits arrive intact in the identifier, which is why the same burst
reads as "protocol violation; bit stuffing error" from the wire and as "bit
stuffing error" alone from the log.

### The speed limit is not just a stored field

45 km/h had been written to `32/03` earlier that day. Stock firmware stops
assisting at 25.0 km/h. On the ride:

```
 43.34  24.9 km/h   12.6 A
 43.59  25.5 km/h   11.6 A
 44.34  26.2 km/h   11.6 A
 44.84  26.6 km/h   11.2 A
```

The cutoff is gone -- the drive unit keeps delivering double-digit current
through and past the speed it used to stop at. The ride topped out at
26.6 km/h, so the new ceiling is untested; what is tested is that the write
changes motor behaviour and not merely a value the tool can read back.

The legal position has not changed and is not this tool's to decide: an EPAC
in the EU assists to 25 km/h. `profiles/m200.py` still flags the value and
still requires `--force`.

### `0x32/0x08` is rider-side, and that is as far as the evidence goes

The table above records `32/08` as non-zero while the shaft turns and not a
speed. The coast-down at the end of the ride narrows it much further:

```
  t     32/08   speed    motor I   cadence   torque
 0.04     42    26.0      0.0 A      69       1238
 0.24     34    26.0      0.0 A      65       1234
 0.44      0    25.2      0.0 A      55       1175
 0.64      0    25.2      0.0 A       0       1164
 2.85      0    15.3      0.0 A       0        859
```

The motor is drawing nothing through every one of those samples, and the field
is still non-zero while the rider is turning the cranks. So it is **not motor
power**. The bike is doing 25 km/h in the rows where it reads 0, so it is
**not speed**. It goes to zero when pedal torque returns to its resting value,
which makes it a rider-side quantity, and it reads like watts -- it peaks at
581 across the ride.

The scale is *not* claimed. Fitting it against `(torque - rest) * cadence` over
the whole ride gives a coefficient spanning an order of magnitude between the
10th and 90th percentile, because `31/00` torque is instantaneous within a
pedal stroke and this field plainly is not. A capture with a steady cadence
against a known crank torque would settle it; nothing here does, so `codecs.py`
still leaves the field undecoded.

### The battery, checked against the drive unit under load

No previous capture in this repository has a pack delivering current. This one
does, and the two nodes agree:

| | battery (`34/00`, `34/01`) | drive unit (`32/00`, `32/01`) |
| --- | --- | --- |
| state of charge | 52% | 52% |
| terminal voltage | 34.87--36.17 V | 34.2--35.5 V |
| current at the peak | 14.92 A | 15.1 A |
| pack temperature | 22 C | -- |
| capacity | 5740 of 11112 mAh, SOH 100% | -- |

Pairing each battery frame with the drive unit frame nearest it in time (within
60 ms, 147 samples) puts the voltage ratio at 0.995 and the current ratio at
1.017 at the median. The remaining spread is sampling lag during fast current
swings, not calibration: the two broadcasts are asynchronous and the current
moves by several amps between them.

That voltage agreement is the useful one. Before the sense-path repair in the
worked case below, the drive unit read 51.50 V against a 37.47 V pack -- a
factor of 1.374. It now agrees with the pack to half a percent, and
`tests/test_ride.py` holds it there.

### What the ride could not settle

`12/00` stayed `00` for all 51 samples, including through braking. That is not
evidence about the field: the brake levers on this bike have no wiring, so
there is nothing for the drive unit to know. Settling the bitfield-versus-fault
-code question needs a bike with electric brake cutoffs, which this one is not.

## Verification loop

Change one field, write it, read it back, and confirm the value moved where
you expected and nothing else did:

```bash
bafang-can dump -o baseline.json          # always start here
bafang-can get Parameter1                 # look at the whole block
bafang-can set Parameter1.current_limit=12    # dry run, prints the payload
bafang-can set Parameter1.current_limit=12 --apply
```

`set` re-reads the block after writing and tells you whether the device agrees.
If a field name in this tool does not map to the byte you expect on your motor,
`bafang-can raw 0x60 0x11` gives you the block as hex and
`bafang-can raw 0x60 0x11 --data <hex> --apply` writes an arbitrary one.

## Diagnosing

```bash
bafang-can diagnose
```

runs the checklist in `profiles/m200.py`:

1. Bus reachable — the drive unit answers a hardware-version read.
2. Identity — hardware/software/model/serial readable and self-consistent.
3. Stored errors — read and recorded *before* anything is cleared.
4. Live electrics — battery voltage with no load, controller temperature.
5. Torque sensor — zero with no foot on the pedal, rising smoothly.
6. Cadence — counts up when the crank turns, no dropouts.
7. Speed — circumference matches the real wheel, speed reads sanely.

For 5 and 6, `bafang-can monitor` is the useful view: pedal gently and watch
`torque` and `cad` move. A torque value that does not return near its resting
number when you take your foot off is the classic sign that the sensor needs
zeroing.

## Calibrating

Torque sensor zero — bike upright, unloaded, no foot on the pedals, cranks
still:

```bash
bafang-can calibrate torque --apply
```

Rotor position sensor — rear wheel off the ground and free to spin, because
the motor turns during the procedure:

```bash
bafang-can calibrate position --apply
```

Both are dry runs without `--apply`. The torque calibration prints the sensor
reading afterwards so you can confirm the new zero.

## Safety limits

`profiles/m200.py` holds conservative guard rails for a 250 W / 36 V class
mid-drive: 18 A current, 32 km/h assist cutoff, 29 V under-voltage floor,
45 V over-voltage ceiling. These are not legal limits — they are the values
past which this tool asks you to confirm with `--force`. What your local law
allows, and what your chassis and drivetrain tolerate, is your call.

The under-voltage floor is the one worth respecting: setting it too low is how
a pack gets over-discharged, and that damage is not recoverable in software.

## Diagnosing an overvoltage fault (a worked case)

A G210 drive unit (reporting itself as `CR X210.350.FC`) displaying error 07
with assist disabled, on a healthy
36 V `BT360` pack. What the bus showed:

| source | value |
| --- | --- |
| `ControllerRealtime1` (32/01), from the drive unit | 51.0 V |
| `BatteryState` (34/01), from the battery | 37.4 V |
| a multimeter on the pack | agrees with the battery |

Two nodes broadcast a voltage for the same pack, and they disagree by a factor
of 1.36. Either the controller block is not laid out the way these codecs
assume, or the controller really does sense high — and a controller that
believes it is seeing 51 V on a 10S pack would trip overvoltage protection,
cut assist and raise a fault, which is exactly the symptom.

`monitor --passive` prints the disagreement instead of either number, because
presenting a confident wrong voltage is worse than presenting doubt.

To decide it, vary the actual pack voltage and watch whether the field
follows. Two points are enough to separate the two ways a sense path fails,
using k and c from a known-good measurement:

* **gain error** (a divider resistor out of spec): reading = k x actual, so
  with k = 1.363 a 31 V supply should read about 42.3 V.
* **offset error** (reference or ADC bias): reading = actual + c, so with
  c = 13.6 V a 31 V supply should read about 44.6 V.

Those predictions differ by more than 2 V, against a measured jitter of
0.1 V, so a single bench run settles it. Power the whole harness from a bench
supply, display included: a drive unit alone does not come up.

Note what this cannot do. That firmware answers identity reads only, so there
is no threshold to inspect, no calibration value to adjust and no stored fault
to clear over CAN. It does *broadcast* the live fault code -- see
[the live fault code](#the-live-fault-code), which would have named this one as
"over voltage protection" on day one. This path characterises the fault for a board-level repair
or a decision to replace the unit; it does not fix it.

### How that case resolved

The field tracks real voltage, scaled high by a constant. Measured at three
supply voltages:

| actual (multimeter) | controller reports | ratio |
| --- | --- | --- |
| 37.42 V | 51.00 V | 1.3629 |
| 35.93 V | 49.00 V | 1.3638 |

The gain model predicted 48.96 V at 35.93 V and was out by 0.04 V; the offset
model predicted 49.51 V and was out by 0.51 V, against a measured jitter of
0.10 V. So the sense path has a **gain error of about 1.363**, not an offset,
and the codecs were reading the right bytes all along.

Bringing the supply down while watching `ControllerState` (12/00) found the
trip point. It toggled seven times around a threshold of roughly **47.0 V as
the controller reads it**, with about 0.5 V of hysteresis, which by the gain
above is **34.5 V of actual pack**. A multimeter agreed: the fault cleared at
34.27 V.

That completes the chain. 47 V is a sensible overvoltage threshold for a 10S
pack charging to 42 V, so the firmware is behaving correctly; the fault is
entirely in the analog sense path ahead of the ADC. A 36 V pack sits above
34.5 V for nearly all of its discharge curve, so the error is permanent in
normal use and assist never engages.

Two cautions on the number. The gain was fitted across voltages spanning only
about 3 V, so a small offset term could hide inside it -- points further apart
would tighten it. And 1.3634 is within 0.02% of 15/11, which is the sort of
ratio standard resistor pairs produce (30k/22k and so on); that is a lead for
checking the divider against a known-good unit, not a conclusion.

### Finding the divider on the board

The controller is inside the motor housing. Once open, the useful move is not
to hunt for likely-looking resistors -- that wasted hours here, and eliminated
four candidate circuits that turned out to be the power path, a lamp driver
and two high-side switches. Work from the constraint instead: **the sense
divider must end at an MCU pin, and its node must move proportionally with the
pack voltage.** Nothing else on the board does both.

On this unit it was a `3002` (30.0 kohm) fed from B+ over a `1.5 kohm` to
ground. With the supply at 34.19 V the node measured 2.199 V:

| quantity | value | meaning |
| --- | --- | --- |
| node / supply | 2.199 / 34.19 = 0.06432 | what the divider actually does |
| node / reported | 2.199 / 46.40 = 0.04739 | what the firmware assumes |
| implied design bottom leg | 1492 ohm | 1.5 kohm to within 0.5% |

That second row is the one that identifies the node beyond doubt. The node
voltage comes from a multimeter and the reported voltage from the drive unit
over CAN, so the ratio between them is the firmware's own calibration constant
read back out of the hardware -- and it landed on a clean 30k/1.5k divider.

### The fault, and what it was not

The bottom leg measured a healthy 1.5 kohm. Working backwards from the
voltages, the top leg was behaving as 21.8 kohm rather than 30 kohm, which
needs roughly **77 kohm in parallel with it**. Removed from the board the
resistor measured 30.5 kohm -- undamaged. The parallel path was contamination
bridging its own terminations, and it left with the resistor.

Refitted, the same measurement gave 40.00 V reported against 39.72 V actual: a
residual **+0.70%**, inside the combined tolerance of two resistors and a
handheld meter. `ControllerState` went to 0 and stayed there.

So the fault that made the bike unusable was a dirt bridge across one resistor.
No component had failed.

### Two measurements that lied

Both cost real time, and both have the same root: **in-circuit resistance
measurement is close to useless on this board**, because every node of interest
has capacitance on it.

* A reading that climbs steadily while you watch it is an ohmmeter charging a
  capacitor, not a resistance. It fooled us twice, once on the KEY divider and
  once on the sense node, where "90 kohm rising to 104 kohm" looked exactly
  like the leakage path we were hunting. The real leakage, computed from the
  drive unit's own reading at full working voltage, was above 5 Mohm.
* Continuity mode will not find a sense divider. It connects to B+ through
  tens of kilohms by design, so a beep test says "not connected" about a wire
  that is very much connected.

What did work, every time: **voltages under power, and components measured
with a leg lifted.** Vary the supply and look for nodes that move
proportionally; that finds the sense chain without tracing a single trace or
identifying a single part number.

## A second fault: the headlight driver

The same unit had a dead headlight, which had failed months before the
overvoltage fault and turned out to be unrelated to it.

The output stage, mapped from the board:

```
B+ -> high-side switch -> buck (6 V) -+-> 2SB772 (PNP) -> QB -> headlight
                                      +-> 2SB772 (PNP) -> WD -> taillight
```

Two identical stages. `QB` and `WD` are the connector pins; WD is 尾灯, the
taillight. Each PNP has its emitter on the 6 V rail, a 10 kohm pull-up holding
the base off, and a base pull-down path of a 3.3 V zener in series with a
2 kohm resistor down to the driver.

The zener in the headlight stage was a glass MELF with a crack through it.
Loose it read open; pressed hard it read 0.7 V forward. That is a switch that
opens when the board flexes -- which is exactly what the symptom had been
saying all along, unheard: the lamp worked with the board on the bench and
died when the board was screwed into its case.

**A fault that changes with position is mechanical.** No component degrades and
recovers. Once the lamp came back out of the case, the search should have
started at cracked parts and joints rather than continuing on component
theory, and it did not.

### Three measurements that lied, again

The pattern from the overvoltage repair repeated, in new forms.

* **An unloaded output reads nothing.** The stage was first condemned on 0 V at
  QB with no lamp connected. An open collector with no load settles on leakage
  and meter impedance; it can read almost anything. Every later conclusion
  about that stage had to wait for a 470 ohm dummy load.
* **A stage that is switched off tells you nothing about how it works.** Two
  full rounds of measurements on the twin stage produced numbers that could not
  be reconciled with any working circuit -- a 0.50 V base-emitter drop
  alongside 0.68 mA of base current, and once an impossible 3.01 V across an
  intact junction. The lights had not been commanded on. Both rounds were
  discarded, and one of them had already produced a confident (wrong) diagnosis
  of an open transistor.
* **A meter's diode range cannot measure a part that is shunted.** In circuit
  the zener reads 1.8 V, because the meter's small test current is fighting the
  10 kohm and 2 kohm around it. The part is a 3.3 V zener. That 1.8 V survived
  several rounds of arithmetic and produced a firm recommendation to fit a 2.4 V
  part, which would have been wrong.

### What did work: a current-limited supply, in circuit

Set a bench supply to 5 mA constant current with a 5 V compliance limit, put
the positive lead on the zener's cathode and the negative on its anode, and
read the supply's own voltage display. It stopped at 3.25 V.

That is the whole measurement, and it is trustworthy for a reason worth
stating: the shunt around the part is about 12 kohm, which at 3.25 V steals
0.27 mA. **Over 94% of the forced current goes through the part.** The meter's
diode range fails at exactly the same task because its test current is small
enough that the ratio inverts.

The compliance limit is what makes it safe on a board with an MCU on it. No
node can be driven above what it already sees in normal operation.

### The reference that settled it

The decisive asset was the *identical twin stage*. The taillight driver is the
same circuit built from the same parts, three centimetres away, and it worked.
Its zener could be measured in place, and its value read straight out of a
working example rather than derived.

A board with two of anything -- two phases, two channels, two supplies -- hands
you a known-good reference for free. Use it before modelling.

### Outcome

Fitted with a BZX55C3V3, leaded rather than MELF because this board demonstrably
flexes, both lights work. The zener value was in the parts box the whole time.
